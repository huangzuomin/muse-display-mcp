## Problem Statement

Muse（云端 AI 助手）目前只能通过 gadget 命令一对一垂直控制单个设备（boox.* 10 条命令）。换设备要改 Muse 端工具定义，加设备要加一批新命令。需求文档 V0.1 已定义目标架构：MCP 语义意图层（display.list_devices / show_text / show_card / show_image / clear / get_status）+ YAML 设备注册表 + Adapter 模式，让 Muse 只描述意图，不感知设备协议、分辨率、字体。首批设备：HoloCubic（240×240 ESP32 全息立方，需新固件）+ BOOX NoteX（10.3" 墨水屏，控制链已全验证）。

定位（D2）：Builder/个人玩票——个人 AI 硬件生态的第一块拼图，自己用为主，长期愿景 Muse Physical I/O（Display 只是第一个模块）。

## What Makes This Cool

- **Muse 有身体**：语义意图推送层在生态里是空档（Tesserae 是计划拉取渲染，EMQX demo 无关联，HA-MCP 不覆盖 ADB 硬化细节）——对话中即时把意图推上实体屏幕，没人做。
- **发光的立方体**：HoloCubic 点亮那一刻是"AI 在场感"的实体化。子代理的洞察：后续"情绪模式"（思考中呼吸白光/完成绿脉冲）= 可编程的 Echo 光环，是比语义推送层更上一层的空档。
- **已验证的底座**：BOOX 控制链（网络 ADB 双地址回退、晨画管线、wqy-zenhei 中文渲染）全部实机验证过，show_image 边际成本近零。

## Constraints

- 树莓派 3B+ 仅 1GB RAM → systemd 原生部署（Python venv + systemd unit + apt mosquitto），否决 docker-compose（D6.1）。
- Muse 云端是否原生支持 MCP 未验证 → 双路预留：MCP 层做成独立服务，tailnet HTTP 直连或 gadget JSON 命令桥接（executor.py 转发）都能进（D4=C，第一天实测）。
- BOOX 硬化约束：深睡断 Wi-Fi、重启后 tcpip 5555 失效、shell 冷启动空输出、screencap 必须落文件——全部封装在 BOOX Adapter 内。
- HoloCubic 需要新固件（风险最高的一环）→ 用 HoloCubic_AIO 社区固件把自建量压到"一个 MuseDisplay app"。
- 安全（需求 §13/§14）：不暴露公网、Tailscale 优先、密钥只进环境变量、日志脱敏。MQTT 链路的安全姿态见下文专节。

### 在线判定与恢复语义

- **HoloCubic**：MQTT 心跳（30s 间隔，status topic）+ broker 遗嘱 LWT（异常掉线时 broker 代发 offline）。90s 无心跳判定 offline。list_devices 的 online 字段来源于此。
- **BOOX**：按需 ADB 探测，复用现有 echo 冷启动探测逻辑（2 次 @1.2s）。深睡期必然表现为 offline——这是正确语义而非故障；e-ink 设备 ping ~30% 丢包不作为离线依据，一律以 ADB echo 探测结果为准。
- **恢复语义**：无缓存重放。offline 期间的新命令立即返回 DEVICE_OFFLINE（含可读 message）；设备恢复上线后后续命令正常执行。online 状态随最近一次探测/心跳刷新，不做主动轮询保活（BOOX 靠按需探测省电，HoloCubic 靠心跳维持）。

### command_id 全链路

MCP 层为每次工具调用生成 command_id（`cmd-<8位随机>`）。MQTT 路径：命令下发与回执均携带。BOOX 路径：Adapter 将 command_id 传入 boox.* 封装调用，返回 payload 与日志行均带回该 id——两条路径同构。日志表含 command_id 列（需求 §14）。

### 设备 failed 回执的 V0.1 行为

V0.1 错误面只内建 OFFLINE/TIMEOUT 两类；设备 ack failed 时的映射：error 字段为内容/渲染类（如 image_decode_failed）→ RENDER_ERROR，其余 → TRANSPORT_ERROR，message 附设备原始 error 字符串与 command_id。补齐轮细分为完整 8 类映射表。

### MQTT 安全姿态

- mosquitto 配双监听器：127.0.0.1:1883（Pi 本机 MCP 服务专用）+ LAN 接口（Pi 的 192.168.50.x 地址，供 HoloCubic 连接）；两个监听器都不含 0.0.0.0，Pi 本身无公网暴露。
- 关闭 anonymous；HoloCubic 设备凭据来自环境变量 MQTT_USERNAME / MQTT_PASSWORD（需求 §13，与 MUSE_DISPLAY_TOKEN 同一套约定，不进仓库）。
- 最小 ACL：设备账号仅可读写 `muse/display/{device_id}/#`；Pi 端 MCP 服务经 127.0.0.1 监听器连 broker（关闭 anonymous + ACL 约束覆盖两个监听器）。
- 远程边界：HoloCubic 是 ESP32 无法入 tailnet，V0.1 明确仅 LAN 内可控；BOOX 远程走 tailnet ADB（已验证）。HoloCubic 的 LAN 外方案列入 Open Questions。

## Success Criteria

V0.1 完成的最小证据（对应需求 §17 MVP 验收）：

1. Muse 同一句 show_text，不改 Muse 端工具定义，分别正确显示在 BOOX 墨水屏和 HoloCubic 立方体上。
2. display.list_devices 返回两台设备，含在线状态（按「在线判定与恢复语义」小节机制）和能力列表。
3. 设备离线时返回明确 DEVICE_OFFLINE 错误（含可读 message）；恢复上线后控制自动恢复（无缓存重放，后续命令正常执行）。
4. command_id 全链路可关联：MQTT 回执带原 id，BOOX 路径返回 payload 与日志同样带回。

补齐项（HoloCubic 调通后立即做，见决策 c8009bd4 升级触发器）：HoloCubic 的 show_card、show_image、get_status 完整版（state/current_content_id，BOOX 侧同步从派生近似升为真实字段）、TTL、SQLite 状态存储、其余 6 类错误码。注：V0.1 已含 MQTT ack 回执（displayed/failed + command_id）；补齐轮的「get_status 完整版」指超出 ack 的状态查询工具，二者不冲突。

### R3-1 — consistency

**Problem**

> 「MQTT 安全姿态」节内部矛盾：『mosquitto 仅绑定 LAN 接口（bind_address 指向 Pi 的 192.168.50.x 地址），不监听 0.0.0.0』与『Pi 端 MCP 服务经 localhost 连 broker』不能同时成立——单监听器绑定 LAN 地址后，127.0.0.1:1883 连接会被拒绝，实现者按文档字面配置会导致 MCP 连不上 broker。

**Remedy**

> 明确双监听器方案（127.0.0.1 与 LAN 地址各一个 listener，均关 anonymous + ACL），或改为 Pi 端 MCP 经 LAN 接口地址连 broker 并说明安全属性不变（流量不出机）。
